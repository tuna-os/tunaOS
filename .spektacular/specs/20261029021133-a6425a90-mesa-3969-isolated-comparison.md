# Feature: 20261029021133-a6425a90-mesa-3969-isolated-comparison

## Overview

Prepare a manually activated comparison of the affected Albacore graphics packages and one upstream repair candidate. Maintainers need controlled evidence of whether software rendering and real desktop login work before the blocked configuration qualification campaign can proceed. This deliverable prepares and verifies the source path only; running the experiment requires separate approval.

## Requirements

- [x] **Explicit activation**
  The lab must refuse execution without separate approval of the exact reviewed source revision and must reject automatic events and retries.
- [x] **Controlled package comparison**
  The lab must compare coherent original and fully patched Mesa sets from fixed inputs using the same baseline and toolchain, refusing identity drift.
- [x] **Rendering and desktop evidence**
  The lab must preserve all four environment controls, report EGL outcomes truthfully, and require visible Wayland login, lock and unlock with positive software-rendering evidence for a repaired verdict.
- [x] **Bounded owned resources**
  The lab must enforce fixed resource/time bounds and clean up only resources it created, including failed and cancelled operations.
- [x] **Trust isolation**
  Test package signing and trust must stay inside owned lab resources without production credentials or publication.
- [x] **Safe evidence**
  The lab must retain bounded allowlisted evidence and reject altered or mismatched transport artifacts.
- [x] **Source-only delivery**
  Preparation must exercise real source-only integrity, refusal and lifecycle scenarios without running package builds, key generation, guests or runtime dispatch, and must not admit automatic image jobs.

## Constraints

- The owner's authorization covers source preparation and ordinary source CI only; executing builds, creating test keys, starting guests, merging or dispatching runtime requires later exact-head approval.
- Use the agreed digest-bound Albacore baseline, exact AlmaLinux Mesa source package and complete upstream two-file patch; retain the existing downstream patches and reject identity drift.
- Reuse the reviewed EGLDevice reproducer and existing visible GDM qualification helpers; preserve the four controls and existing gate deadlines.
- Keep the agreed build profile at 8 CPU, 80 GB and 180 minutes, and sequential KVM runtime at 60 minutes, with no automatic retries.
- Test-signing trust belongs only in owned lab images and guests; production credentials and trust are unavailable.
- Never upload VM disks, private keys or ISOs; retain only explicitly bounded allowed artifacts.
- Preserve the existing implementation lanes, automatic image-admission rules, user changes, active ISO workflow and frozen existing verification assets.

## Acceptance Criteria

- [x] **No implicit execution**
  Automatic events, absent or mismatched revision approval, and repeated attempts fail before any privileged or expensive operation.
- [x] **Reproducible comparison identity**
  Fixed source inputs, baseline, toolchain and complete control/candidate package identities are recorded; any mismatch refuses comparison.
- [x] **No false repair verdict**
  Candidate crashes, absent software-renderer evidence or incomplete visible desktop transitions cannot produce a repaired result. A missing DRM match is reported as such, never as EGL success; control failures remain visible.
- [x] **Cleanup and bounds**
  Timeouts and failures produce bounded reports and remove owned resources without deleting unrelated resources or publishing secrets/disks/ISOs.
- [x] **Trust boundary**
  Only a temporary lab public key reaches test images; no production trust, R2 object or public package/image changes.
- [x] **Transport integrity**
  Tampered, oversized, path-traversing, linked or identity-mismatched artifacts are refused before consumption.
- [x] **Verified source candidate**
  A complete executable manual path, meaningful safety tests, source-only smoke evidence and ordinary source CI are delivered without running the experiment. Exact-head runtime approval and runtime results remain explicitly absent.

## Technical Approach

- No technical direction is settled beyond the captured constraints; the plan will choose a small isolated manual harness and fail-closed activation mechanism without adding a production lane.

## Success Metrics

- Source-only safety scenarios and affected verification pass with no package builds, key generation, guests or runtime dispatch.
- The published source candidate admits zero automatic image/guest jobs under the unchanged routing rules.
- A later separately approved run yields one bounded paired report with exact identities and all required rendering/desktop observations, or an explicit failure; no unsupported repair claim is produced.

## Non-Goals

- This lab does not diagnose the missing encrypted-boot unlock prompt or qualify native/browser ISO installation; those existing acceptance obligations remain open.
- This lab does not complete the TOML/configuration epic or replace its blocked eight-image campaign.
- This lab does not change public download routing, package delivery architecture or browser build optimizations. These remain separate work, not silently removed from the overall objective.
