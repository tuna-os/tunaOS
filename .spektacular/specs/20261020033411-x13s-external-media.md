# Feature: 20261020033411-x13s-external-media

## Overview

Provide external live test media for the ThinkPad X13s Gen 1 so its owner can evaluate TunaOS without changing the existing internal installation. Include the boot dependencies and a verifiable recovery path, and state which results still need physical testing. Keep later installation, update and rollback evidence distinct from the initial live test.

## Requirements

- [ ] **Complete boot payload**
  The system must supply the board firmware, drivers and kernel-matched device description needed for external live boot.
- [ ] **Persistent boot settings**
  The system must preserve the approved board arguments across live boot and later installed deployments.
- [ ] **Verifiable artifact**
  The system must bind each test artifact to immutable image, builder and installer identities and verify downloaded components and media against their integrity and trust evidence.
- [ ] **Safe first test**
  The owner can boot external media without automatic installation or automatic mounting of internal storage. Guidance must explain the write risk of a manual desktop mount.
- [ ] **Honest status**
  The system must distinguish source checks, artifact checks, generic virtual-machine checks and real X13s results.
- [ ] **Deployment continuity**
  The design must retain a compatible kernel, device description and initramfs after installation, a kernel update and rollback.
- [ ] **Actionable test guidance**
  The owner can find the exact download, integrity checks, recovery steps, known limits and result checklist for the artifact under test.

## Constraints

- The qualification epic #3368 limits this target to ThinkPad X13s Gen 1 / SC8280XP and the ARM64 Bonito profile.
- The epic requires an explicit test window and recovery access for physical boot tests; initial installation uses a spare external SSD.
- The epic requires redistributable firmware, retained speaker gain limits and explicit user opt-in for modem FCC unlock.
- The epic rejects generic ARM64 virtual-machine results and driver enumeration as proof of SC8280XP hardware operation.
- The epic requires a kernel-matched device description across deployments; a fixed one-time ESP copy cannot satisfy rollback.
- Existing repository policy requires signature and qualification gates, behavioral regressions, and an approved design before a cross-area boot-path change lands.

## Acceptance Criteria

- [ ] **Payload gaps block release**
  Artifact inspection rejects the wrong architecture, absent board firmware, absent required early-boot drivers and mismatched kernel/device-description payloads.
- [ ] **Arguments survive deployment**
  The live artifact and each later installed test deployment report the approved board arguments without a remoteproc blacklist.
- [ ] **Artifact identity is reproducible**
  The test bundle supplies the final media digest, immutable component identities, component/media trust-verification results and a complete payload report. This does not assert Secure Boot.
- [ ] **External live boot remains non-destructive**
  A physical test records cold boot, built-in input, graphics and networking with internal-storage automount disabled and without an installer action or manual internal-disk mount.
- [ ] **Results cannot inflate support**
  Missing hardware results remain explicitly unqualified even when the source, artifact or generic virtual-machine checks pass.
- [ ] **Lifecycle evidence remains explicit**
  Plain and passphrase-encrypted external installations, a kernel-changing update and rollback each record the matching boot payload and baseline hardware results before installed support is claimed.
- [ ] **The owner can report the first test**
  Guidance names the exact external artifact, integrity checks, safe boot and recovery steps, known limits and a concise result checklist. It labels the first live test experimental. The inspected artifact may be delivered before the owner supplies the physical result; hardware support remains unqualified.

## Technical Approach

- Follow the epic's preference for the stock Fedora kernel before a custom kernel fork.
- Extend the existing ARM64 Bonito profile and normal image/media pipeline rather than create an unrelated distribution path.
- Evaluate the Fedora shim/GRUB and kernel-embedded DTB direction documented by W1 against the installed deployment lifecycle before adoption.
- Prefer Fedora-packaged firmware and its redistribution notices over manual firmware extraction.

## Success Metrics

- The owner completes the experimental external live test and returns a result tied to the exact artifact.
- The initial live test leaves the existing internal installation usable and unchanged.
- Every published support claim has a matching artifact or physical result; absent evidence stays visible as an open gate.

## Non-Goals

- This work does not alter the reference laptop's partitions, firmware, persistent boot configuration or security settings. The owner may manually select external media in the temporary boot menu.
- Initial media does not promise Secure Boot, TPM auto-unlock, KVM, reliable suspend, camera, modem, fingerprint, external display or video-decoding support.
- This work does not add automatic installation, automatic modem unlock, or an unreviewed Windows-firmware redistribution path.
- Full installed-system qualification remains open until the later physical installation, update and rollback tests pass.
